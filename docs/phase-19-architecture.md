## Request and monitoring flow

```text
Request -> fresh generated REQ context -> existing auth/service/PG transaction
  -> timed checkout/provider/stock/kitchen/delivery stages
  -> original safe business result or normalized error + X-Request-ID
  -> scrubbed JSON events (never body/cookie/query/provider payload)
  -> unexpected 5xx: best-effort safe incident + optional scrubbed tracking adapter

Authenticated scheduler -> REQ + JOB context -> original idempotent processor
  -> JobRun RUNNING -> SUCCEEDED / PARTIAL / FAILED
  -> deduplicated job incident / recovery
  -> operational monitor checks existing queue/journal/refund/job state

Verified current SUPER_ADMIN -> read-only bounded PG snapshot
  -> health cards + safe references, never raw log text or business-state override
```

For example, two delivery workers claiming the same ready paid order produce one success and one 409 warning, with separate request IDs. A database outage instead produces safe unavailability, while liveness stays responsive. A failed notification delivery retains its outbox retry state without reversing that paid order. These different causes should not all look like an unexplained 500.

## Requested 75 topics

### 1. What Phase 18 achieved\n\nPhase 18 added organization/customer branding, safe logos, location settings and staff invitation/role/grant/suspension controls. Firebase retained credentials; PG retained current authorization. Its security version, last-admin safeguards and audits are preserved rather than rebuilt.\n\n### 2. Phase 19 purpose\n\nProvide diagnosable reliability: identify what/where/when failed and its safe correlation. This is not a new commerce flow, order state, financial KPI, scaling system, CI/CD pipeline or final penetration-hardening phase.\n\n### 3. Structured logger\n\nlogger.ts emits one JSON object per line. Context, safe operation/entity fields, classification, timing, environment and release replace important ad-hoc server console objects. Free-form bodies/messages/stack traces are deliberately excluded; console remains only the controlled sink.\n\n### 4. Log levels\n\nDebug is suppressed in production; info records completed stages, warn records expected conflicts/retry problems, error records unexpected availability/internal failures. A 409 double claim is not promoted to a catastrophic error or global UNHEALTHY state.\n\n### 5. Request correlation\n\nEvery application API export is wrapped by observedRoute. It generates a REQ-UUID and uses AsyncLocalStorage to carry it through nested awaits and services. Incoming IDs are ignored, avoiding spoofed correlation. X-Request-ID and safe errors expose the same reference.\n\n### 6. Background job correlation\n\nA scheduled processor obtains JOB-UUID under the same observation context, retaining the originating request ID. Outbox attempts and completion/failure logs share that context. Job correlation is diagnostic, never authentication or a work ownership lease.\n\n### 7. Business-entity correlation\n\nUse internal order/payment/refund/event identifiers only when the service already has legitimate context. Public order code can identify checkout/transition work. Do not log a raw anonymous token, QR credential, setup URL or attacker-selected foreign entity details on denial.\n\n### 8. Redaction\n\nsafe.ts recursively scrubs sensitive keys and drops unknown text, bounds object/array depth and accepts only controlled telemetry fields. Headers, cookies, card data, contact details, notes, payloads, cryptographic material and error messages/stacks are excluded. It is deny-by-default rather than relying solely on secret-name regexes.\n\n### 9. Query-string safety\n\nRoutes log static operation names instead of request.url. Path sanitization strips all queries/fragments and replaces non-allowlisted segments with [id], including seat credentials. No arbitrary query allowlist or raw URL is forwarded to tracking.\n\n### 10. Error normalization\n\nKnown validation, ServiceError, Prisma/driver and identity categories map to safe codes/status/retryability. Unknown exceptions become UNKNOWN_INTERNAL_ERROR with a generic message. Raw SQL/provider text is not copied into a response or incident record.\n\n### 11. Error boundaries\n\nMajor admin, customer, kitchen, delivery and platform areas use RecoveryPanel; root/global fallbacks also exist. They expose recovery and a validated Next digest, not error.message/stack. Customer broad catches now return null only for expected 401/404; dependency failure reaches recovery UI.\n\n### 12. HTTP status handling\n\nExisting semantic ServiceError statuses remain intact, including 401/403/404/409/422/429/500/503. Constraint and transaction conflicts are 409, missing records 404, connection/schema/timeouts 503. Safe references help support without granting access.\n\n### 13. Liveness\n\nGET /api/health returns only status:ok, no-store and request header. It checks responsiveness, not external dependencies; a database outage must not cause a process liveness restart loop. It writes no audit/notification/incident record.\n\n### 14. Readiness\n\nGET /api/ready validates critical current server configuration and a bounded PostgreSQL SELECT 1 transaction. It returns safe 503 unavailable on failure. This is not a probe of payment/Auth/Storage reachability, queue completeness or migration reconciliation.\n\n### 15. Public health security\n\nBoth public probe bodies are controlled/minimal. No host, database name, connection URL, provider topology, exception text or private repository/release data is disclosed. Public probe failures are excluded from incident persistence so probes cannot manufacture business/audit history.\n\n### 16. Internal health\n\nCurrent verified SUPER_ADMIN may query /api/super-admin/operations or view /super-admin/operations. The service independently rechecks the role; cached shell navigation is not authority. The internal DTO contains bounded operational summaries, not raw logs.\n\n### 17. Database health\n\nThe probe records monotonic latency and check time without raw SQL values. Connect acquisition is bounded; local statement timeout and transaction/max-wait limits constrain the probe. Configurable degraded latency defaults to 500ms, a diagnostic choice rather than SLA.\n\n### 18. Prisma classification\n\nP2002/P2003 become safe conflict, P2025 not-found, known serialization/deadlock conflict stays retryable, and known connection/timeout/missing-schema errors become unavailable. Wrapped driver/originalCode and initialization errorCode are recognized without parsing a secret-bearing message.\n\n### 19. Webhook monitoring\n\nActual receive, verification, processing and failure stages emit safe correlated logs. The dashboard uses the existing PaymentWebhookEvent journal and separates internal cancellation recovery. Unverified bodies do not become trusted settlement records, and rollback failures may exist only in logs/incidents.\n\n### 20. Duplicate webhook classification\n\nThe existing provider/event unique key and settlement locks retain idempotency. Replays log webhook.duplicate instead of a failure. They do not create a second payment history, consume stock twice or trigger kitchen eligibility twice.\n\n### 21. Provider failure logging\n\nThe provider boundary times create/retrieve/cancel/refund calls and normalizes unexpected provider exceptions to a safe retryable unavailable error. PG connection failure retains its database classification. No raw authentication payload, card data, provider secret or full external ID payload is logged.\n\n### 22. Refund monitoring\n\nRead existing Refund status and retry chain, not an invented provider ledger. Unresolved FAILED rows and old PENDING/PROCESSING counts are visible; a failed predecessor with a linked retry is excluded. Attention age uses createdAt because recovery deliberately rotates updatedAt.\n\n### 23. Outbox monitoring\n\nRead pending count, oldest pending age, retrying count and final failures from Phase 17 outbox. Its committed business event remains authoritative even if delivery fails. Dashboard health can degrade notifications without claiming the order/payment rolled back.\n\n### 24. Stuck-event detection\n\nBacklog threshold defaults to 120 seconds, old work/refunds to 900 seconds, stale scheduled run to 300 seconds. All are bounded server configuration. Age is based on actual persisted timestamps; empty or missing history is not replaced by fabricated timestamps.\n\n### 25. Background job health\n\nTrack the notification scheduler, payment recovery scheduler and new diagnostic monitor. Record last success/failure/partial, counts/duration and current/recent run status. JobRun model\n\nOnly operational lifecycle/count/reference/environment/release data is stored.
