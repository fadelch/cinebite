# CineBite

CineBite will allow cinema customers to order food and have it delivered directly to their seats.

## Current phase

**Phase 2 — Multi-Tenant Firestore Architecture**

Phase 2 defines the tenant-aware Firestore hierarchy, domain types, runtime validation, server repositories, and default-deny database rules. Authentication begins in Phase 3; this phase does not create users, login screens, or client-side database access.

## Domain model

An **Organization** is the cinema company, such as a brand that owns multiple branches. A **Location** is one physical branch. Each location contains its own **Halls**, and each hall contains its own **Seats**.

```text
organizations/{organizationId}
  locations/{locationId}
    halls/{hallId}
      seats/{seatId}

users/{uid}
```

CineBite separates Organization from Location because a company can operate many physical cinemas. Company-wide policy belongs to the organization, while addresses, timezones, halls, staff access, and future inventory belong to individual locations. Treating each branch as a separate top-level company would duplicate company data and make cross-location administration difficult.

### Organization

Represents one cinema company. Its document stores a stable generated ID in the Firestore path, a changeable human-readable name, a URL-safe slug, a restricted lifecycle status, and server timestamps.

### Location

Represents one physical cinema belonging to exactly one organization. The parent organization is enforced by its nested document path. The returned TypeScript model includes `organizationId` for application context, but that ID is derived from the path rather than trusted as document data.

### Hall

Represents an independently managed auditorium inside a location, including its number, status, and seat count.

### Seat

Represents a seat inside one hall. Rows, positive seat numbers, matching labels such as `G12`, and restricted statuses are validated. QR tokens are intentionally deferred.

### UserProfile

Prepares the shape of a future `users/{uid}` document. A profile will connect a Firebase Authentication UID to an organization, permitted locations, and one restricted role. No user records or authentication logic are created in Phase 2.

## Tenant isolation

Tenant scope is part of every nested repository path and method signature. A location is loaded with:

```ts
getLocationById(organizationId, locationId)
```

There is intentionally no `getLocationById(locationId)` operation. This prevents application code from accidentally querying a location without first establishing organization context. The organization ID will come from verified authorization context in a later phase, not from an untrusted browser field.

Document IDs are generated by Firestore. Names are not used as IDs because names can change. Slugs are separate, validated URL identifiers.

## Validation and timestamps

Zod schemas validate all creation input before a repository writes it. Schemas reject unknown fields, which prevents callers from supplying tenant IDs or authoritative timestamps. The Admin SDK writes `createdAt` and `updatedAt` using Firestore server timestamps.

Firestore documents are parsed again when read. The mappers attach path-derived IDs and prevent unchecked `document.data() as Model` casts from spreading through the application.

## Firestore security

`firestore.rules` denies every browser read and write by default. Phase 2 performs database work only through the server-only Firebase Admin repository layer. Admin credentials never use `NEXT_PUBLIC_` variables and must never be committed.

The queries introduced in this phase use Firestore's automatic single-field indexes, so `firestore.indexes.json` intentionally defines no custom composite indexes.

## Setup

1. Install dependencies:

   ```bash
   npm install
   ```

2. Copy `.env.example` to `.env.local`.
3. Add Firebase client values from **Firebase Console → Project settings → General → Your apps → Web app**.
4. Add Firebase Admin values from **Firebase Console → Project settings → Service accounts → Generate new private key**. Copy `project_id`, `client_email`, and `private_key` into their matching variables. Keep the private key quoted if it contains escaped `\n` characters.
5. Run the application:

   ```bash
   npm run dev
   ```

The health check is available at `GET /api/health`.

```env
NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID=

```

Server-only values:

```env
FIREBASE_ADMIN_PROJECT_ID=
FIREBASE_ADMIN_CLIENT_EMAIL=
FIREBASE_ADMIN_PRIVATE_KEY=
```

Phase 2 adds no environment variables.

## Manual Firebase step

Review `firestore.rules`, then deploy the rules and index configuration to the intended Firebase project using the Firebase CLI when deployment is explicitly authorized. They are not deployed automatically by this branch.

## Security

`.env.local` must never be committed. Firebase Admin credentials are server-only. Service-account JSON and private key files are ignored by Git. Production secrets will be configured in Vercel project settings when deployment begins.
